# Decision Record

本文件記錄專案的設計決策（Architecture Decision Record, ADR）。每項決策將闡述其決策內容、背景理由，以及技術權衡與否決方案。翻譯服務的設計見 [`DesignDocument.md`](DesignDocument.md)，微調程式的設計見 [`DesignDocument_Finetune.md`](DesignDocument_Finetune.md)。

## Decisions

### ADR-0001：生成資料以 JSON Lines 儲存記錄列表

* **決策：** 生成資料以記錄列表儲存，每筆是含 `zh`、`en` 欄位的 JSON 物件；檔案格式採用 JSON Lines (JSONL)：UTF-8 編碼，每行一筆，無外層陣列。
* **理由：** 資料結構需滿足五項業務需求：(1) 同一句中文允許多個可接受的英文翻譯；(2) 支援擴充 Metadata（如 `id`、`origin`）；(3) 英文句子中會包含 ASCII 逗號與引號；(4) 雙向翻譯（`en→zh` 與 `zh→en`）共用同一筆資料，方向於匯出時才決定；(5) 具備容錯力，格式錯誤時可定位到特定單行。在 Python 標準的 JSON 解析中，重複的 key 會被靜默覆蓋，而傳統 CSV 在處理含逗號的英文句子時極易發生欄位錯位，皆無法滿足需求。
* **代價：** 本決策犧牲了「能使用試算表直接開啟審稿」以及「利用 `json.load` 一次性載入全檔」的便利性，以換取「支援逐行讀取」與「能精確回報格式錯誤所在行號」的優勢。若未來新增寫入功能，因 JSONL 不支援純粹追加寫入的原子性操作，必須採取整檔覆寫（寫入暫存檔後透過 `os.replace` 取代）。
* **否決：** 以中文句子為 key 的 dict（重複 key 會被靜默覆蓋、無處存放 metadata、方向被迫寫死）；`zh` 與 `en` 兩個平行陣列（對齊只靠 index，漏刪一邊會導致後續全數錯位且難以偵測）；CSV（處理英文逗號易錯位，且每增加一種 metadata 就需牽動 Schema）；單一 `.json` 陣列檔（單一語法錯誤會導致整個檔案無法載入，且增減記錄會牽動相鄰的尾端逗號，擴大 `git diff` 的範圍）。

### ADR-0002：中文欄位存繁體，訓練匯出時轉簡體

* **決策：** 生成資料的 `zh` 欄位僅存繁體。匯出訓練集時，透過 `ScriptConverter.to_simplified()` 轉成簡體，作為 `en→zh` 的 target 與 `zh→en` 的 source；實體資料檔不儲存簡體。
* **理由：** 審稿與參考詞彙表皆以繁體為單一來源。簡體與繁體的轉換並不對稱（如「髮」與「發」皆轉為「发」，反向還原需依詞彙上下文判斷），因此技術上只能由繁體決定性地單向推導出簡體。此外，經實驗證實，直接以簡體中文作為模型目標端，能有效降低 Token 消耗量與未知字元（`<unk>`）的發生機率。
* **代價：** 本決策導致資料檔中儲存的 `zh` 內容（繁體）與模型實際訓練時所接收的字串（簡體）在字形上不一致；以此為代價，換取在人工審稿與資料儲存時，只需維護唯一的繁體版本（單一事實來源，SSOT）。
* **否決：** 資料檔直接存簡體（逐筆審稿的結果無法無損還原為繁體）；同時存繁體與簡體兩欄（破壞 SSOT 原則，兩欄容易失去同步，且簡體完全可由繁體運算得出）；直接以繁體為訓練目標（導致 Token 消耗量激增，降低推論效率）。

### ADR-0003：`source_lang` 與 `target_lang` 皆為必填

* **決策：** `TranslationRequest` 的 `source_lang` 與 `target_lang` 欄位皆為必填，且須指定為 `LanguageMap` 中已定義的成員。當兩者相同時，將由資料驗證層（Pydantic）直接拒絕，請求不會進入 Domain 層。
* **理由：** 翻譯方向必須由使用者明確指定。為確保 API 的擴充性，請求的欄位集合需要具備穩定的形狀（Shape），以確保未來加入第三種語言時，系統介面不需發生破壞性變更。系統亦不打算實作語言自動偵測。
* **代價：** 本決策犧牲了 API 呼叫的極致簡潔度（每次請求皆需明確指定兩個欄位），以換取未來擴充語系時，API Request 的結構能保持向後相容。
* **否決：** 僅指定一端語言並由系統推斷另一端（加入第三種語言時，原有的 Request 結構將面臨語意模糊與破壞性修改）；以自動偵測取代必填欄位（自動偵測僅適合作為輔助功能，不應取代核心的必填參數）。

### ADR-0004：離線環境變數在 `transformers` 匯入前設定

* **決策：** `infrastructure/_offline_env.py` 在被匯入時，利用 `os.environ.setdefault` 將 `HF_HUB_OFFLINE` 與 `TRANSFORMERS_OFFLINE` 設為 `1`。所有使用到 Hugging Face 生態系的 Adapter 必須在匯入 `transformers` 之前先匯入該模組。
* **理由：** 目標環境為實體隔離網路，而 `AutoTokenizer.from_pretrained` 在遇到本地模型路徑缺失時，預設會無聲地向外發出網路請求。由於 `transformers` 等套件會在匯入階段就將環境變數固化為模組常數，因此若等到應用程式啟動後才設定環境變數將無法生效。
* **代價：** 本決策引入了模組匯入順序的強耦合（`_offline_env` 必須嚴格先於 `transformers` 匯入，並需以 `isort: skip` 避開 Linter 自動排版）；以此為代價，確保當本地模型檔案缺失時，底層套件絕對不會嘗試發起對外的網路連線。
* **否決：** 在程式主進入點或匯入套件後才設定變數（此時底層函式庫已將變數轉為常數，設定無效）。

### ADR-0005：記錄的 `id` 使用 UUID4

* **決策：** 記錄的 `id` 採用 `uuid.uuid4().hex`（32 個小寫十六進位字元）。由建立該記錄的一方產生一次後，即永久固定。
* **理由：** `id` 需要滿足三項嚴格要求：(1) 在同一個方向資料夾下的所有檔案之間必須絕對唯一（留出集切分會依賴 `id` 雜湊排序，且 `load_all()` 遇重複 `id` 會拋出錯誤）；(2) 文字內容被校正或修改後，`id` 仍須保持不變；(3) 同一句中文允許多個可接受的英文翻譯，因此輸入端完全相同的句子會對應多筆獨立記錄。
* **代價：** 本決策犧牲了流水號的高可讀性；以此為代價，換取在多檔案產製與分散式環境下，記錄 ID 能夠自然達到全局唯一，免去跨檔案協調衝突的維護成本。
* **否決：** 每個檔案各自獨立的流水號（合併載入時會發生 ID 衝突）；基於校正後文字的 Hash 值（文字被修改時 ID 會隨之改變，違反要求 2）；基於輸入端句子的 Hash 值（無法處理一對多的合理翻譯，違反要求 1 與 3）。

### ADR-0006：以 `Seq2SeqTrainer` API 在 Infrastructure 實作微調

* **決策：** 微調流程在 Infrastructure 層以 `transformers` 的 `Seq2SeqTrainer` API 實作（實作 Domain 定義的 `ModelTrainer` 介面）。訓練所需的 `torch` 與 `accelerate` 僅限安裝於訓練機環境，不列入專案的 `pyproject.toml`。訓練程式 `train()` 會在內部動態檢查相依套件。
* **理由：** 官方提供的 `run_translation.py` 腳本在不同版本間存在取得不穩定的問題，且要求特定的 jsonlines 格式，不易與專案資料流整合。考量到推論端僅需 CPU 且記憶體受限，將龐大的機器學習訓練框架從執行期依賴中剝離是必要的。
* **代價：** 本決策放棄了在核心專案虛擬環境中直接執行訓練的便利性（避免強迫翻譯服務安裝龐大的機器學習套件與模型權重）；以此為代價，換取專案相依清單與推論環境的純淨度，同時確保資料轉換與訓練編排邏輯，能在完全沒有安裝 `torch` 的環境下透過 Fake 物件進行單元測試。
* **否決：** 以 subprocess 呼叫 `run_translation.py`（取得腳本方式不穩定，且透過檔案介面交換資料無法進行 Fake 測試）；沿用 `models/*-ct2/` 量化模型（原始張量未保留，無法作為微調基底）。

### ADR-0007：記錄轉成訓練契約的字串處理放在 Domain

* **決策：** Domain 層的純函式 `build_training_pairs` 全權負責將記錄轉換為 `TrainingPair` 的四項字串處理：(1) 折疊連續空白與去頭尾；(2) 透過 `ScriptConverter` 將中文轉簡體；(3) 依翻譯方向對齊 source 與 target；(4) 捨棄空字串記錄。CLI 僅負責解析參數；`HfSeq2SeqTrainer` 僅接收 `TrainingPair` 並執行斷詞與訓練。
* **理由：** 若將字串清洗與轉換邏輯放在 CLI 層，CLI 將違反薄介面（Thin UI）的設計原則；若將其放在底層訓練 Adapter，轉換規則就會與 `torch` 環境死綁在一起。
* **代價：** 本決策引入了額外的 Domain 型別（`TrainingPair`）並犧牲了一份完整的記憶體副本空間；以此為代價，換取字串轉換規則完全與 CLI 或底層訓練函式庫脫鉤，確保純邏輯能在無 `torch` 依賴的環境下進行單獨測試。
* **否決：** 在 CLI 層處理字串（導致轉換規則只能透過命令列參數進行端到端測試）；在訓練 Adapter 內處理字串（轉換規則綁定 `torch`，大幅增加測試難度與執行時間）。

### ADR-0008：留出集以 chrF 評分，並在 Domain 自行實作

* **決策：** Domain 層的純函式 `chrf_score` 自行實作了 chrF 評分演算法（基準參數對齊 `sacrebleu` 2.6.0 的預設值）。該函式透過比對字元 n-gram 計算 precision 與 recall，得出 0 至 100 的整體分數。
* **理由：** 系統需要一個客觀指標來量化模型對未見句子的翻譯能力提升。指標必須能處理無空白分詞的中文，且評估過程不應新增對外部套件的依賴。chrF 直接比對字元 n-gram，完美避開了中文分詞的難題。
* **代價：** 本決策犧牲了直接使用現成套件的便利性，必須自行維護一份評分演算法實作；以此為代價，換取專案不需新增 `sacrebleu` 依賴，並維持無 `torch` 環境下的快速單元測試能力。
* **否決：** 直接使用 `sacrebleu`（強制新增相依套件）；BLEU（必須先決定並實作中文分詞，且分數對分詞方式極度敏感）；神經網路指標如 COMET、BERTScore（需額外引入龐大的評估模型與依賴環境）。

### ADR-0009：留出集依 `id` 的 hash 決定性切分

* **決策：** `split_holdout` 會將全部記錄依據 `sha256(f"{seed}:{id}")` 的雜湊值進行排序，並依設定比例切分出「留出集（Holdout Set）」，其餘記錄則進入訓練集。
* **理由：** 切分邏輯必須具備 100% 的可重現性（以利跨次評估基準對齊），且不能依賴實體檔案的先後順序（使用者可能會手動搬移行數）。此外，為保持專案結構簡潔，不應為評估資料新增獨立的實體檔案。
* **代價：** 本決策導致留出集完全由 `id` 與 `seed` 的雜湊值決定而無法人工精確指定（且當資料集總量變動時會影響切分結果，導致跨時間點的分數僅在「資料不變」時才具備可比性）；以此為代價，換取切分結果與實體檔案順序無關、具備決定性（Deterministic），且不需額外維護獨立的評估檔案。
* **否決：** 取檔案最後 N 筆（高度依賴檔案順序，手動搬行即破壞基準）；每次執行使用亂數抽樣（不可重現，無法進行 A/B 模型對比）；獨立的評估檔（增加檔案同步與維護負擔，且需防範資料外洩至訓練集）。

### ADR-0010：翻譯服務不處理專有名詞，由微調後的權重提供

* **決策：** `TranslateTextUseCase` 對輸入原文僅呼叫 `TranslationEngine.translate()` 一次，過程中不進行任何代理詞鎖定、替換或還原。專有名詞的譯名呈現完全交由微調後的模型權重自行發揮。翻譯服務在執行期（Runtime）完全不讀取參考詞彙表。
* **理由：** 早期採用代理詞鎖定與替換機制，會導致模型在訓練階段無法學習到真實的軍事專有名詞上下文分佈。為使模型能原生處理這些術語，決議移除此替換機制。此外，經實驗證實，直接以簡體中文作為模型輸入，能顯著降低 Token 消耗量與未知字元（`<unk>`）的發生率。
* **代價：** 本決策放棄了在執行期絕對保證專有名詞 100% 準確出現的強制力；以此為代價，換取移除複雜的代理詞替換機制，藉此打破單次請求最多只能處理 16 個詞彙的系統瓶頸，並消除了模型輸出因隨機抽取代理詞而產生的不穩定浮動現象。
* **否決：** 維持代理詞鎖定與替換（阻礙模型學習真實術語分佈，且存在處理上限）；保留鎖定機制為可選功能（增加維護成本與邊界案例）；`zh→en` 不轉簡體直接送入繁體（導致 Token 消耗量大幅增加，且與來源端的訓練字體脫鉤）。

### ADR-0011：生成資料的來源以檔名主檔名標記，載入方向資料夾下所有 JSONL

* **決策：** 每份生成資料（`*.jsonl`）視為一個獨立來源，並以檔名主檔名作為該批記錄的 `origin` 欄位標記（例如：`llm_generated.jsonl`）。載入程式會直接讀取特定方向資料夾下的所有檔案並投入訓練，系統不提供透過參數（旗標）過濾特定來源的功能。
* **理由：** 為確保資料的一致性與品質，現行架構已廢除人工與機器混合生成的舊分類機制，全面改為由教師 LLM 產製資料。為滿足資料溯源需求，每個產生者獨立一個檔案加上 `origin` 欄位即足以識別。
* **代價：** 本決策犧牲了透過執行參數靈活選擇資料來源的控制力，且單筆記錄不再綁定模型版本；以此為代價，換取系統具備「新增產生者時只需新增檔案、無須修改程式碼」的高擴充性。若需排除特定來源，僅需在檔案系統層級移除或重新命名該檔案即可。
* **否決：** 程式碼內硬編碼來源列舉（違反開閉原則，新增來源時需同步修改程式碼）；保留納入旗標過濾機制（當前架構已無須排除特定來源的需求）；單一檔案混合儲存並依賴欄位標記（違反分開儲存的溯源要求）。

### ADR-0012：以術語命中率作為第二個評估指標

* **決策：** 評估報告除了計算 chrF 分數外，另引入「術語命中率（Term Hit Rate）」。程式將比對輸入來源與參考答案，找出「預期詞條」，並檢驗該詞條的譯名是否精確出現於模型輸出中。為防止一般單字造成誤判，系統設定了嚴格比對規則（如：全名至少需 2 個單字，中文詞條剔除括號備註等）。
* **理由：** 微調的核心目標在於提升軍事專有名詞的翻譯準確度，而傳統的 chrF 分數容易將專有名詞的錯誤稀釋在整個句子的字元匹配中，無法有效反映改善程度。透過專屬的術語比對規則，能更精準地量測模型對術語學習的吸收率。
* **代價：** 本決策導致教師模型若自行偏離詞彙表（如將 U.S. 譯為「美軍」而非詞彙表規定的「美國」），該詞將無法計入評估基準，且極短縮寫的誤判只能仰賴手動調整詞彙表來防堵；以此為代價，換取與教師模型共用單一事實來源（SSOT）、不新增外部依賴，並確保雙向翻譯評估能共用同一套純邏輯。
* **否決：** 僅依賴 chrF 評估（專有名詞的改善程度完全被隱藏）；放寬全名字數限制（會因一般單字產生大量偽陰性誤判）；強制進行中文整串精確比對（包含括號與註解的詞條將永遠無法命中）。

### ADR-0013：上游 LLM 的資料目錄依流向命名，生成資料依翻譯方向分資料夾

* **決策：** 資料目錄的命名嚴格反映資料的角色與流向。例如，教師句對放置於 `data/llm_generated/<source>_to_<target>/`，目錄名稱明確對應教師模型接收的語言與產出的語言。微調指令將依賴此目錄結構載入對應方向的資料。
* **理由：** 若將所有句對檔混雜在同一層目錄，將無法區別該筆資料是「英翻中」還是「中翻英」的產物。清晰的資料夾命名與分離，確保了資料溯源與訓練流向的絕對正確性。
* **代價：** 本決策犧牲了「將同一批句對直接用於反向訓練」的靈活性，且產生了一份教師規則的副本（增加同步維護的成本）；以此為代價，換取資料流向的絕對清晰（來源側一律等於教師接收的語言），並大幅降低與外部網頁版 AI 介接的操作成本（僅需上傳詞彙表與明確對應的資料檔）。
* **否決：** 扁平的單一資料目錄並依賴旗標切換（資料夾無法反映語言方向，容易造成反向訓練的災難）；將翻譯方向寫入單一檔名（破壞來源統計機制）；使用過於通用的命名如 `training_pairs` 或 `ai_generated`（無法表達資料的未審閱狀態與真實產製者）。
